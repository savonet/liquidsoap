# Findings index

Ranked index of every finding in this directory, with the result of an adversarial verification pass. Ranking: data loss, then security and resource exhaustion, then correctness, then the rest. Within a rank, findings verified by a run come first.

Verdicts:

- **Confirmed (run)**: reproduced by this pass with a bounded script (scripts and outputs in `/var/tmp/claude-ffmpeg-spec/verify/`).
- **Confirmed (code)**: the code path was re-read from scratch and admits no other reading; the author's run, when there is one, is consistent with it.
- **Worse**: confirmed, and the effect is wider than the finding states.
- **Narrower**: confirmed, and the effect is smaller or more specific than stated.
- **Unverified**: re-read, but the claim depends on runtime behaviour that could not be run here (reason given).
- **Not reviewed**: outside the top set; the author's status stands.

Last column: what the original author did (checked / read only).

## 7. Deduplication groups

Each group is one finding, owned by the first area; the others link to it.

- **A. Per-step truncation in the `Duration` helper.** Owner [common](common.md) ("Duration chunks drift against timestamps"). Same root: decoder "Copy chunk lengths drift", inline-codecs "Chunk lengths truncate per packet", decoder To verify "effect on encoder output". The helper's other two faults travel with it: `flush` keeps its list (common) and `flush` returns length 1 with no packets (filters, bitstream flush). Every user of the helper (copy and raw decoders, inline encoders, bitstream filters, filter graph I/O) inherits all three.
- **B. Readiness scheme.** Owner [encoder](encoder.md) D2. D3 is the other half of the same design: the count is compared to every copy track of the format, so only the D2 override lets anything start. One fix must address both.
- **C. GC-dependent per-source identity.** Owner [encoder](encoder.md) G1. Inline-codecs "Stream index after sleep depends on the GC" is the same mechanism on the producer side (`SourceIdx`), feeding the encoder's `Stream` store.
- **D. Container start time ignored.** Owner [decoder](decoder.md): "Seek target ignores the container start time" and "Remaining time is short by the container start time" share `position ()`/`set_remaining` using absolute PTS against a 0-based duration. "Subtitle positions absolute, advance positions relative" is a third face of it.
- **E. Transform lifetime.** Owner [inline-codecs](inline-codecs.md) "Transform persists across tracks"; content "Inline producer doc comment vs behaviour" is the same.
- **F. Content with `params = None`.** Owner [content](content.md) (whether such content exists). Linked: encoder G4, filters "Bitstream filter on content without parameters", inline-codecs "Raw decoders on content without full parameters", common "`track.ffmpeg.side_data` before parameters".
- **G. Field numbering across probe and decoder.** Owner [decoder](decoder.md) "Field numbering differs between probe and decoder"; content "Field numbering shifts when a stream fails to describe" is the same.
- **H. Data fields offset by subtitle count.** Owner [content](content.md); decoder "Data fields numbered after subtitles" is the same.
- **I. Missing end-of-stream drains** (related, distinct sites, each its own fix): inline tail (2), encoder re-framer (3), raw decoder (4), copy A/V tail (5), internal decoder resampler (9), interleave pending list (10), `input.ffmpeg` EOF (11), samplerate converter (16), fps converters (17). Common pattern: the `Duration` helper and every converter hold back data that only an explicit flush releases, and several callers never send it.
- **J. Last copied audio packet** (5): reported by encoder G8 and cross-file C8, owned by decoder.

## 8. Per-source `Weak` store: verdict

Re-read of `mk_stream_store` (`encoder/ffmpeg_encoder_common.ml:47-100`) and `mk_stream_copy`:

- Strong references: each copy track holds exactly one record, its `current_stream`. A record stays in the set while at least one track has it as current.
- GC cannot forget a record still needed: a sibling switching to source S looks S up only after some track switched to it first, and that track holds it. Forgetting while needed happens only through the explicit `remove` (D5, narrower than reported).
- No permanent leak: entries are weak; the initial record for id `0` is shared by all tracks and dropped at their first switch.
- GC-dependent revival: when every track has left S and S comes back under the same id (inline encoder after sleep, Ogg restart), the result depends on collection (group C).
- `Stream.merge` in `remove` re-inserts a record that was already collected, then removes or decrements it: harmless but it can resurrect a count from a holder's copy.
